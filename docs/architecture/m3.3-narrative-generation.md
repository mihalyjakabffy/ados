# ADOS-M3.3 — Narrative Generation

## 1. What this milestone is, in one sentence

The first genuinely generative layer in ADOS, bounded to answering
exactly one question — what should this document say, in what order,
with what emphasis, using which verified project content, for which
audience — and stopping there, before "how should it look" (M3.4) or
"which commands execute it" (M3.5) begin.

```
SemanticIntent (M3.1) + ContentIntelligenceModel (M3.2) -> NarrativePlan (M3.3) -> (future M3.4) -> DesignIntent
```

## 2. The architectural boundary, enforced structurally

No `NarrativePlan` field names a page, a coordinate, a grid, a font, or
a colour. No module in `brand/llm/narrative/` imports
`brand.creative.intent`, `brand.creative.composer`,
`brand.creative.scope`, `brand.creative.iterate`, or
`brand.creative.plan` — verified by an AST walk over every module's own
import nodes (`tests_brand/test_narrative_boundaries.py`), the same
technique ADOS-M3.1/M3.2 already established, not a docstring promise.
The same test also asserts no module defines a `CommandIntent`,
`PagePlan`, or `DesignIntent` class, and checks the schema itself for
field names that look like layout (`page`, `grid`, `column`, `font`,
`colour`).

## 3. Why a new package, not an extension of M3.1's `LLMProvider`

`brand.llm.provider.LLMProvider` is hard-typed to
`(SemanticContext) -> SemanticIntent` — a narrow, single-purpose
contract, not a generic seam. ADOS-M3.2 already solved the "reuse the
Claude client without creating a second one" problem the right way: the
module-level `get_client()`/`call_structured()` functions in
`brand.llm.providers.claude_provider`, generic over whatever pydantic
`output_format` a caller passes. `brand.llm.narrative.generation`
reuses that exact seam — no second Claude client, and `NarrativePlan`
never touches an Anthropic SDK type.

## 4. Reused vocabulary vs. new vocabulary (`brand/llm/narrative/vocabulary.py`)

* **`Audience` is reused as-is** from `brand.creative.direction` —
  ADOS's one existing, canonical audience vocabulary
  (client/peer/authority/public/internal), already read downstream by
  `CreativeDirection` itself. Reusing it means a `NarrativePlan`'s
  audience is immediately usable by M3.4 to select a matching
  `CreativeDirection`, with no second mapping layer.
* **`NarrativeObjective` is new** (introduce/explain/persuade/document/
  present/compare/summarize/demonstrate) — `CreativeDirection.Goal`
  (inform/persuade/record/instruct) is a coarser, layout-facing concept
  that cannot represent the master prompt's own worked example
  (`objective: introduce`). `sell`/`educate` from the master prompt's
  list are folded into `persuade`/`explain` — distinct English words,
  not a distinct communication objective, per the master prompt's own
  "do not create an unnecessarily large uncontrolled vocabulary."
* **`SectionRole` is new** (16 values, the master prompt's own §11
  list, verbatim) — deliberately not `brand.content.model.BlockRole`
  (context/problem/intervention/outcome/evidence/detail/provenance):
  that enum names a single already-composed `ContentBlock`'s role, a
  physical-composition-layer concept; `SectionRole` names a whole
  pre-layout section's rhetorical purpose. A few names overlap because
  both are, at bottom, rhetorical vocabulary — that does not make them
  the same field.
* **`SectionPriority`, `Requirement`, `Relevance`, `Tone`,
  `NarrativeVoice`, `MissingImpact`, `ExclusionReason`,
  `NarrativeIssueType`, `NarrativeCompression`** are all new, small,
  closed vocabularies with no existing ADOS equivalent, each sized to
  the master prompt's own worked list.

## 5. Domain model (`brand/llm/narrative/model.py`)

`SCHEMA_VERSION = "3.3"`. All models frozen, `extra="forbid"`.

* **`ContentReferenceSet`** — `fact_ids`/`claim_ids`/`asset_ids`/
  `entity_ids`, plain strings pointing at real
  `brand.llm.content.model` objects. The provenance chain the master
  prompt asks for (`NarrativeSection -> ContentReference -> ContentItem
  -> SourceReference`) is realised without a redundant indirection
  layer: a M3.2 `Fact`/`Claim`/`AssetContent` already *is* the
  addressable content item and already carries its own `source_refs`
  inline, so "a section references content id X" plus "X's own
  ContentIntelligenceModel entry carries source_refs" already is that
  chain.
* **`NarrativeSection`** — `role`, `purpose` (more important than
  `title`: it is the answer to "why does this section exist"),
  `sequence`, `priority`, `requirement`, `audience_relevance`,
  `content_refs`, `emphasis`, `subsections` (ADOS-M3.3 §23's
  hierarchical expansion), and an optional, capped `draft`.
* **`GeneratedClaim`** — a `model_validator` makes it structurally
  impossible to construct one with `status=VERIFIED` (a generated claim
  is interpretive by construction) or with empty `supporting_refs` (an
  unsupported generated claim must be omitted, not represented) —
  ADOS-M3.3 §15, enforced the same way ADOS-M3.2 §8's hallucination
  guard is: at the constructor, not by convention.
* **`NarrativeThesis`** — a plain `statement` + `supporting_refs`.
  `NarrativePlan.thesis` is `None` when the available content cannot
  support one (ADOS-M3.3 §8) — representing the limitation directly
  rather than writing an ungrounded sentence. Unlike `GeneratedClaim`,
  the model itself does not block an unsupported thesis from being
  *constructed*; `brand.llm.narrative.validation`'s NAR-006 catches
  that independently, and `_materialize` (§7 below) never lets one
  survive into a returned plan in the first place.
* **`NarrativeMissingInformationImpact` / `NarrativeIssue` /
  `NarrativeExclusion`** — each a plain-value read of a M3.2 concept
  (a `MissingInformation` key, a conflicting fact, an excluded item),
  never a live reference — a `NarrativePlan` must stay self-describing
  when read back out of a trace with no `ContentIntelligenceModel` in
  hand.
* **`NarrativePlan`** — carries `content_model_version` +
  `content_resolved_at` (ADOS-M3.3 §46: which content-model snapshot
  this plan reasoned over), `objective`, `audience` + `audience_label`
  (the closed enum plus the original free-text nuance, e.g.
  "prospective_client"), `tone`, `voice`, `thesis`,
  `narrative_strategy` (an ordered `tuple[SectionRole, ...]` — the same
  pattern `CreativeDirection.narrative_order` already uses for
  `BlockRole`, applied one semantic layer up), `compression`,
  `sections`, `generated_claims`, `missing_information`,
  `narrative_issues`, `exclusions`.

**The critical architectural test (ADOS-M3.3 §36).** A `NarrativePlan`
must remain fully meaningful with every `draft` field deleted —
verified directly by
`test_narrative_model.py::test_plan_remains_meaningful_with_every_draft_field_deleted`.

## 6. Context assembly (`brand/llm/narrative/context.py`)

```
SemanticIntent -> Content Resolution (M3.2) -> scoped ContentSummary -> NarrativeGenerationContext
```

`summarize_content()` shrinks an already-resolved
`ContentIntelligenceModel` to ids, keys, statuses, and short text —
never the whole project (ADOS-M3.3 §33). Superseded facts are omitted
entirely.

**Audience is resolved once, deterministically, here — never
re-derived by a generator.** `resolve_audience()` maps free-text labels
("prospective_client", "investor", "competition_jury", "architect",
"academic", "internal_team", "general_audience", ...) onto the reused
`Audience` enum via a fixed keyword table, defaulting to `PUBLIC` (the
most conservative assumption) when nothing is stated. This exists
because the master prompt's own §7 requires that audience "must NOT
alter factual truth" — the strongest way to guarantee that is to make
audience a stable *input* to generation, not something a
possibly-non-deterministic LLM call re-derives on every request.

`resolve_objective_hint()` is a similar, softer keyword mapping from
`SemanticIntent.purpose`/`action` to a `NarrativeObjective` — a *hint*
`RuleBasedNarrativeGenerator` uses directly (having no reasoning of its
own to fall back on) and `LLMNarrativeGenerator` receives as guidance
but may still override, since choosing an objective is genuine
narrative reasoning, unlike audience classification.

## 7. Generation (`brand/llm/narrative/generation.py`)

```
NarrativeGenerator.generate(context) -> (NarrativePlan, ProviderMetadata | None)
```

Two implementations, mirroring `brand.llm.content.extraction`'s own
split:

* **`RuleBasedNarrativeGenerator`** — deterministic, no network call.
  ADOS-M3.3 §44 is explicit this is a CI-determinism/schema/regression
  fixture, not a claim of narrative sophistication. It builds a fixed
  role sequence — from a small per-document-type lookup table when the
  document type is one of four known ids (realising the master
  prompt's own §21/§41 worked strategy shapes: portfolio =
  concept-driven, client-presentation = problem→concept→development→
  impact, competition-document = question→concept→strategy→evidence→
  result, design-report = context→problem→technical_explanation→
  result), else a compression-based shape (short/medium/long) — and
  fills each section's `content_refs` from whatever facts/claims the
  content summary actually offers, flagging any conflicting fact as a
  `NarrativeIssue` rather than ever referencing it directly.
* **`LLMNarrativeGenerator`** — Claude, via `call_structured()`.

**The anti-hallucination mechanism is structural, mirroring ADOS-M3.2's
own.** The LLM's structured-output schema (`RawNarrativePlan` and its
nested `Raw*` types) may only name a fact/claim/asset/entity **id** —
never a value, a status, or source text — and has **no audience field
at all**. After the call returns, `_materialize()` drops (never
trusts) any id that does not actually appear in the `ContentSummary`
the LLM was given, drops a thesis whose support turns out to be
entirely invented, and omits a generated claim whose support turns out
empty. A section whose every reference turns out to be invented ends
up with empty `content_refs` — a plan-shape a human reviewer or
`brand.llm.narrative.validation` can immediately see is thin, never a
silently-fabricated fact.

## 8. Prompt (`brand/llm/narrative/prompt.py`)

`PROMPT_VERSION = "3.3.0"`. Ten-part system prompt (role, the
`NarrativePlan` semantics, narrative vocabulary, fact/claim/generated-
claim rules, provenance rules, audience rules — "fixed for you
already, do not re-derive it" — narrative-strategy examples, output
schema, and failure behaviour), plus a trust-boundary section
identical in spirit to ADOS-M3.2 §31: the content summary is data,
never instructions.

## 9. Deterministic validation (`brand/llm/narrative/validation.py`)

Reuses `brand.validation.brand_validator`'s `Finding`/`Severity`/
`Category`/`ValidationReport` — the one validation framework every
other ADOS validator already uses. Eight checks (`NAR-001`..`008`):

| Code | Severity | Checks |
|------|----------|--------|
| NAR-001 | ERROR | duplicate section id (including subsections) |
| NAR-002 | ERROR | two sections at the same level share a `sequence` |
| NAR-003 | ERROR | a content reference (section, thesis, generated claim, issue, or exclusion) does not resolve in the given `ContentIntelligenceModel` |
| NAR-004 | ERROR | a section references a fact whose M3.2 status is `conflicting` without a matching `narrative_issue` |
| NAR-005 | BLOCK | a generated claim with no supporting refs — the independent, "two layers that don't share code" re-check of the model's own constructor rule |
| NAR-006 | BLOCK | a thesis with no supporting refs |
| NAR-007 | WARN | a `required` section whose purpose is too short to explain why it exists |
| NAR-008 | WARN | a factual-role section (evidence/technical_explanation/comparison/result/impact) with no content references, when not marked optional |

## 10. Planning orchestrator (`brand/llm/narrative/planning.py`)

```
plan_narrative(project, content, semantic_intent, *, document_type_id="",
               compression=MEDIUM, generator=None, request_id=None) -> NarrativePlan
```

```
assemble_narrative_context -> generator.generate (falling back to
    RuleBasedNarrativeGenerator on ProviderError) -> stamp
    content_model_version/content_resolved_at -> validate_narrative_plan
    -> record_narrative_trace -> NarrativePlan
```

Never resolves content itself — `content` is a required argument,
produced by `brand.llm.content.resolution.resolve_content` (M3.2)
before this function is ever called. Not a second content-resolution
system, per the master prompt's own explicit instruction.

## 11. Observability and regeneration (`brand/llm/narrative/observability.py`)

Extends ADOS-M3.1/M3.2's exact in-memory, bounded trace pattern:
request id, project/content-model version, a semantic-intent summary
(**field names only**, never values — the same "never store
unnecessary sensitive content" posture M3.2's own observability
commits to), model, prompt version, the full resulting plan, validation
outcome, latency.

**This is also ADOS-M3.3 §46/§47's regeneration mechanism.** A
`NarrativePlan` is not written into any `Project`/`Document` store by
this milestone — every `plan_narrative` call produces an independent,
fully-formed plan with its own id, and the trace list is how a previous
plan remains inspectable after a regeneration. This is a deliberate
scoping decision (see §14 below), not an oversight.

## 12. API (`api/routers/narrative.py`)

```
POST /api/v2/ados-projects/{project_id}/narrative/plan
     {semantic_intent, document_id?, document_type_id?, version?,
      compression?, user_corrections?, raw_documents?}
     -> {narrative_plan, content, validation, request_id}
GET  /api/v2/ados-projects/narrative/schema      -> {schema_version, schema}
GET  /api/v2/ados-projects/narrative/traces      -> {traces: [...]}
GET  /api/v2/ados-projects/narrative/traces/{id} -> one trace
```

Mounted at the same `/api/v2/ados-projects` prefix
`content_intelligence.py` already uses. `semantic_intent` is given as
its own JSON shape (this endpoint *consumes* an intent; it does not
extract one from raw text — that is `POST /intent/semantic`'s job).
Internally calls `resolve_content()` (M3.2) with the same
`document_id`/`document_type_id`/`version`/`user_corrections`/
`raw_documents` parameters `content_intelligence.py` exposes, then
`plan_narrative()` — never a duplicated resolution path. The response
never contains a `plan` (PagePlan-shaped) or a `command_intent` key.

## 13. Evaluation (`brand/llm/narrative/evaluation.py` + `tests_brand/data/narrative_eval.json`)

Eleven cases covering all ten of the master prompt's §41 acceptance
scenarios (A–J, with Case H split into two cases — client and jury —
since it is inherently a two-request comparison): the four
document-type strategy shapes (A–D), missing information surfaced (E),
conflict surfaced (F), the unsupported-claim trap (G), audience
transformation (H), and narrative compression (I). Case J (an existing
ADOS-generated document must not be elevated to verified truth) is
covered at the unit level in
`test_narrative_planning.py::test_case_j_existing_ados_document_is_not_elevated_to_verified_truth`,
since it is a property of what `ContentSummary` reports (status, not
source identity), not something a document-type/compression case needs
to re-derive.

The harness scores content-reference validity/grounding (the same
number, reported under both of §42's names — see the module's own
docstring for why: `_materialize` already guarantees every surviving
reference is valid by construction, so this is verified empirically
rather than assumed), strategy fit, audience accuracy, missing-
information detection, conflict detection, coverage (the fraction of
available facts/claims actually referenced somewhere in the plan),
redundancy (the fraction of references used by more than one section),
hallucination rate, schema validity, and domain-validation success —
against the deterministic `RuleBasedNarrativeGenerator` on every CI
run — currently 100% on every gated metric, **0% hallucination rate**.
`scripts/run_narrative_eval.py` runs the identical dataset against the
real Claude-backed `LLMNarrativeGenerator` for a human to read whenever
an API key is available — never part of the automated suite.

## 14. Known limitations and scoping decisions (stated honestly)

* **No `NarrativePlan` storage.** This milestone does not add a new
  persistence surface into `Project`/`Document` for narrative plans —
  every `plan_narrative()` call is independent and stateless, and
  regeneration history lives in the observability trace list, not a
  versioned store. The master prompt's own §47 asks only that
  regeneration "not corrupt previous plans" and that they "remain
  inspectable" — the trace store satisfies both without inventing a
  parallel versioning concept for an object this milestone does not
  otherwise wire into the Project/Document/Version lifecycle.
* **`RuleBasedNarrativeGenerator`'s per-document-type strategy table is
  intentionally small** (four entries) — enough to prove the master
  prompt's own four worked examples deterministically in CI; the real
  narrative-strategy reasoning is `LLMNarrativeGenerator`'s job once
  `ANTHROPIC_API_KEY` is configured.
* **Coverage/redundancy/coherence are reported, not gated** in the CI
  test suite — they are informative deterministic metrics (ADOS-M3.3
  §25: "use deterministic metrics first"), but the master prompt sets
  no numeric target for them the way it does for hallucination rate
  (0%), so no arbitrary threshold is enforced.
* **No LLM-as-judge evaluation** is implemented — ADOS-M3.3 §25
  explicitly allows it only as an *additional*, not sole, mechanism,
  and the deterministic metrics above already cover every §42 metric
  this milestone can check without one.

## 15. Readiness for M3.4

`NarrativePlan` is exactly the artifact M3.4 needs: a sequenced,
prioritised, fully-sourced communication plan with facts, claims, and
gaps already resolved, so that "how should this become a visual
design" never has to re-derive "what should we say" from scratch. The
boundary this milestone commits to — `NarrativePlan` and nothing
layout-shaped below it — is exactly where M3.4 begins.
