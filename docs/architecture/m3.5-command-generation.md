# ADOS-M3.5 — Command Generation

## 1. What this milestone is, in one sentence

Given a `DesignIntent` (M3.4) and the real, current `DesignState` (M2.5), compile the small set of already-existing, already-validated `CommandIntent`s (M1.2) — never a new command type — that would move the real document toward what the `DesignIntent` describes, and let a human or a caller apply them through the execution path that already exists.

This is a compiler, not an agent: it never composes, never applies on its own initiative, and never proposes a lever the shipped `brand.creative.intent`/`brand.creative.composer` stack cannot already execute.

## 2. The architectural boundary, enforced structurally

Three things stay apart, mirroring the M1.2 `brand/creative/intent.py` split this milestone builds directly on top of:

- **Command** — a `DesignIntent`'s semantic field (a `composition_strategy`, a `density`, a `SectionDesign.image_density`). Never reaches the Composer.
- **Intent** — a real, validated `brand.creative.intent.CommandIntent`, produced by this package (`brand/llm/command/`).
- **Execution** — `validate_intent()` → `apply_intent()` → `compose()`. This package's own modules (`generation.py`, `planning.py`, `validation.py`) never call the last two; only `api/routers/command.py`'s one `/commands/apply` endpoint does, and `tests_brand/test_command_boundaries.py` proves this at the AST level (`test_no_command_module_composes_or_applies`, `test_router_generate_and_validate_endpoints_never_compose_or_apply`).

`validate_intent()` is the one function this package *does* call from two independent places: `planning.py` (every command is re-checked before it is ever placed on a returned `CommandPlan`) and `validation.py`'s CMD-001 (an independent re-check that does not trust `planning.py`'s own filtering). `test_generation_and_validation_functions_only_call_validate_intent` asserts both call sites still exist — a regression there would mean this package stopped re-checking its own output.

No arbitrary code execution: `test_no_command_module_executes_arbitrary_code` forbids `eval`/`exec`/`subprocess`/`os.system`-style calls anywhere in the package and its router.

## 3. The central finding from repository reconnaissance: two content models, one narrow bridge

Before writing any code, this milestone's Phase 0 read `brand/creative/intent.py` (`CommandIntent`, `validate_intent`, `apply_intent`), `brand/creative/scope.py` (`compose_scoped`, `diff_pageplans`), `brand/creative/iterate.py` (M1.4/M1.5's `RecommendationCapability`/`IterationResult` pattern), and `brand/design_state/model.py`. Two things fell out of that reading that shaped every decision below:

1. **`CommandIntent` (M1.2) is a document/page-scoped nudge schema**, not a per-section authoring schema. Its eight `IntentType`s operate on a `brand.content.model.ContentModel` (a flat set of `ContentBlock`s, id pattern `[a-z]{3}-\d{2,3}`) and a `CreativeDirection` — never on a `NarrativePlan` section or a `DesignIntent.SectionDesign`.
2. **There is no bridge between `SectionDesign.content_refs`/`asset_refs` (M3.2's fact/claim/asset id space) and `ContentModel.ContentBlock.id`.** `ContentBlock` carries a free-text `provenance` field, not a structured back-reference to the fact/claim/content-item it came from. No shipped code resolves one id space to the other.

Given ADOS-M3.1 through M3.4's own anti-hallucination discipline (never invent a mapping/bridge that does not already exist), this milestone does **not** invent that bridge. `brand/llm/command/__init__.py`'s own docstring states this explicitly. The consequence: this compiler operates at **document scope**, diffing three real, closed-form `DesignIntent` signals against the real, already-composed `DesignState` — never at per-section/per-block granularity. Section-level design decisions with no document-wide expression are recorded as skipped, with a reason, never guessed at.

This is the single largest scoping decision of the milestone, and it is the reason the resulting `CommandPlan`s are small (0-3 commands) rather than one-per-`SectionDesign`.

## 4. Vocabulary (`brand/llm/command/vocabulary.py`)

Reused directly, not re-declared: `IntentType`, `TargetType` (`brand.creative.intent`), `ScopeType` (`brand.creative.scope`, imported for its enum value only — `compose_scoped`/`resolve_scope` themselves are never imported here).

New, and why an existing vocabulary did not already cover it:

- `CommandSafetyLevel` (`safe`/`review_recommended`/`destructive`) — M1.2's `CommandIntent` has no safety classification; ADOS-M3.5 requires one. `SAFETY_BY_INTENT_TYPE` is a fixed table (`REMOVE_CONTENT` → destructive, `CHANGE_PAGE_DIRECTION` → review_recommended, everything else → safe), so a claimed safety level is a checkable fact (CMD-009), not a per-command judgement call.
- `CommandProvenance` — which real signal produced a command: a structural diff, an LLM disambiguation, a design issue, a design constraint.
- `CommandRejectionReason` — why a candidate lever did *not* become a command: already matching, ambiguous, stale state, failed re-validation, no safe automatic remedy.
- `DIRECTION_BY_COMPOSITION_STRATEGY` / `TARGET_TEXT_DENSITY_BY_LEVEL` / `TARGET_IMAGE_RATIO_BY_LEVEL` — deterministic lookup tables anchored to the three shipped `CreativeDirection`s' own real values (`text_density`/`image_ratio` of `editorial-quiet`/`technical-dense`/`image-led`), not invented targets.

## 5. Domain model (`brand/llm/command/model.py`)

- `GeneratedCommand` — wraps one real `CommandIntent` with `safety_level`, `provenance`, `source_field` (the exact `DesignIntent` field that drove it — reference, never restatement), `rationale`, and `idempotent` (whether *regenerating* against the resulting state converges — true for direction swaps and false, by design, for a literal-replay of a continuous nudge; see the class docstring for the precise distinction).
- `SkippedLever` — a candidate this package considered and did not act on, with a reason. Every lever a `DesignIntent` names either becomes a command or a `SkippedLever`; nothing is silently dropped.
- `CommandPlan` — the root object: `project_id`, `design_intent_id`, `design_state_version` (copied from the source `DesignIntent`, used for staleness checks), `commands`, `skipped`, `metadata`.
- `CommandExecutionStep` — built only by the API's `/commands/apply` route from the real `IntentResolution` `apply_intent()` already returns; never constructed by `generation.py`/`planning.py`.

## 6. Context assembly (`brand/llm/command/context.py`)

`CurrentVisualState` reads exactly the fields `resolve_current_visual_state()` needs from a real `DesignState`: `version.number`, `document.direction_id`, `visual_language.text_density`/`image_ratio`, `len(pages)`. Nothing else — the same "shrink and organise, never re-derive" posture `brand.llm.design.context` already established for Brand/CreativeDirection.

## 7. Generation (`brand/llm/command/generation.py`)

`RuleBasedCommandGenerator` is the primary and normally sufficient generator — deterministic, no network call, and the only generator most `CommandPlan`s ever need. It computes exactly three independent candidates per call:

1. **Direction** — `composition_strategy` → `DIRECTION_BY_COMPOSITION_STRATEGY` → one `change_page_direction` command, or a skip (`NO_CHANGE_NEEDED` if already matching, `AMBIGUOUS_MAPPING` for `BALANCED`/`ASYMMETRIC`/`MODULAR`/`SEQUENTIAL`/`IMMERSIVE`, which have no single confident direction).
2. **Density** — `density` vs. `current.text_density`, gap computed against `ados.fill_ratio_bounds()` the same way `apply_intent()`'s own density math does, so the predicted post-state matches what `apply_intent()` will actually produce; emits `increase_text_density`/`reduce_text_density` or skips as `NO_CHANGE_NEEDED` when the gap is inside `NEGLIGIBLE_GAP`.
3. **Image emphasis** — the *mode* of every `SectionDesign.image_density` (a real aggregate of real per-section data, not an invented root-level field) vs. `current.image_ratio`; emits `increase_image_emphasis`/`decrease_image_emphasis` or skips.

Every real `DesignIssue` is additionally recorded as a `SkippedLever` with reason `NO_SAFE_COMMAND_EXISTS` — a flagged brand conflict is real information for a reviewer, and this compiler does not guess a fix for it (ADOS-M3.5's own "compiler, not agent" boundary, made concrete).

`LLMCommandGenerator` reuses the shared Claude client (`brand.llm.providers.claude_provider`) for exactly one bounded call: when the deterministic pass left the direction lever `AMBIGUOUS_MAPPING`, it may ask the model to choose among the three already-registered direction ids, or decline. Its structured-output schema (`RawDirectionChoice`) has a field for nothing else — no parameter, no target, no new `IntentType` — so a hallucinated answer has nowhere to go: `_materialize_choice` drops any id outside the closed, already-known set (`UNKNOWN_DIRECTION`) and falls back to leaving the lever skipped. Density and image-emphasis candidates, and every design-issue skip, are untouched by this generator — it only ever adds or changes the one ambiguous decision.

## 8. Prompt (`brand/llm/command/prompt.py`)

`PROMPT_VERSION = "3.5.0"`. Deliberately narrow: the system prompt states the three known direction ids and instructs the model that naming anything else, or proposing a command/parameter/target, is outside the task and will be discarded.

## 9. Deterministic validation (`brand/llm/command/validation.py`) — CMD-001 through CMD-010

`validate_command_plan()` returns the same `brand.validation.brand_validator.ValidationReport` every ADOS validator does. Ten checks:

| Code | Severity | What it checks |
|---|---|---|
| CMD-001 | BLOCK | Every command independently re-passes the real `validate_intent()` — the load-bearing check. |
| CMD-002 | ERROR | No plan contains both an increase and a decrease/reduce for the same metric. |
| CMD-003 | BLOCK | `remove_content` never appears with an empty rationale — no deletion by implication. |
| CMD-004 | BLOCK | A page-targeted command's index is inside the given page count. |
| CMD-005 | BLOCK | `plan.design_state_version` matches the state it is about to be checked/applied against. |
| CMD-006 | BLOCK | No parameter value hides a colour or dimension (reuses the hex/dimension regex pattern `brand.creative.direction` already uses). |
| CMD-007 | WARN | Every command carries a non-empty rationale. |
| CMD-008 | ERROR | No rationale itself leaks a dimension/colour/coordinate. |
| CMD-009 | BLOCK | A command's claimed `safety_level` matches `SAFETY_BY_INTENT_TYPE` — safety-label integrity. |
| CMD-010 | WARN | More than four non-safe commands in one plan — a minimality nudge, not a hard cap. |

## 10. Planning orchestrator (`brand/llm/command/planning.py`)

`plan_commands(design_intent, content, *, design_state=None, generator=None, request_id=None)`:

1. Assembles context.
2. **Version-safety short-circuit**: if `design_intent.design_state_version` disagrees with the current `DesignState`'s version, generation does not run at all — every lever a stale diff could compute is suspect, not just one of them. The plan carries a single `STALE_DESIGN_STATE` skip.
3. Runs the generator (`_default_generator()` picks `LLMCommandGenerator` only when `COMMAND_GENERATION_LLM_ENABLED` is not disabled and `ANTHROPIC_API_KEY` is set — otherwise, and on any `ProviderError` at runtime, `RuleBasedCommandGenerator`).
4. Re-validates every proposed command via `validate_intent()` before it is ever returned; a failure drops the command and adds a `VALIDATION_FAILED` skip rather than trusting the generator.
5. Records an observability trace and returns the `CommandPlan`.

## 11. Observability (`brand/llm/command/observability.py`)

The same bounded in-memory `deque` trace pattern every M3 layer uses (`_MAX_TRACES=200`), and for the same reason: no `CommandPlan` is persisted into any Project/Document store, so the trace list is this milestone's own regeneration/history mechanism.

## 12. API (`api/routers/command.py`)

Generation and execution are two different endpoints:

- `POST /{project_id}/commands/generate` — resolves content (M3.2) → narrative (M3.3) → `DesignIntent` (M3.4) → `DesignState`, then `plan_commands()` + `validate_command_plan()`. Never calls `apply_intent`/`compose` (proven at the AST level, function-scoped, in `test_router_generate_and_validate_endpoints_never_compose_or_apply`).
- `POST /{project_id}/commands/validate` — re-runs `validate_command_plan()` against a caller-supplied plan/content/state, on demand.
- `POST /{project_id}/commands/apply` — the one endpoint that calls the real `validate_intent()` → `apply_intent()` → `compose()`, sequentially, for some or all of a plan's commands. Every command is re-validated immediately before it is applied; the first failure stops the sequence.
- `GET /commands/schema`, `GET /commands/traces[/{id}]`.

Both `/commands/generate` and `/commands/apply` require the caller to supply `content_model` inline (a `brand.content.model.ContentModel` payload) — there is no `ContentModel` store in this repository (`api/routers/brand.py`'s own `/intent`/`/iterate` endpoints already establish this convention), and it is a structurally different object from the `ContentIntelligenceModel` the M3.2-M3.4 pipeline resolves (see §3).

## 13. Frontend (`ados-web/app/dev/command-generation/page.tsx`)

Mirrors `/dev/design-intent`'s shape: inputs for project/document id and an inline `content_model` JSON payload, a "POST /commands/generate" action showing the compiled commands (type, target, safety label, provenance, rationale), the skipped-lever list, and the validation report — plus a second, separate "POST /commands/apply" action that is disabled until a plan with at least one command exists, showing the resulting per-step execution and the final composed page count.

## 14. Evaluation (`brand/llm/command/evaluation.py` + `tests_brand/data/command_eval.json`)

Ten cases (A-J), run against the deterministic `RuleBasedCommandGenerator` (CI-safe, no `ANTHROPIC_API_KEY`, no network — there is deliberately no LLM-backed eval script the way M3.4's `run_design_intent_eval.py` has one, since this package's LLM path only ever disambiguates a direction the deterministic pass already found ambiguous, and every dataset case is deliberately either confident or ambiguous-and-skipped):

- **A** — a confident strategy with no prior `DesignState` still proposes a direction.
- **B** — a `DesignIntent` that already matches the current state produces zero commands.
- **C** / **D** — a real density gap produces the correctly-signed increase/decrease.
- **E** — an ambiguous strategy produces zero direction commands and a recorded `ambiguous_mapping` skip — zero hallucination.
- **F** — a stale `design_state_version` blocks generation entirely.
- **G** — the modal `SectionDesign.image_density` drives image emphasis.
- **H** — a `brand_conflict` design issue is recorded, never silently auto-"fixed".
- **I** — a composite case forcing three simultaneous levers, all independently re-validated.
- **J** — no `DesignState` at all still proposes a confident direction, nothing else.

Metrics: `case_accuracy` (exact expected-vs-actual command-type set match), `schema_validity_rate`, `hallucination_rate` (a command names a direction/parameter this package's own closed tables never produced), `unsafe_execution_rate` (a command's `safety_level` disagrees with `SAFETY_BY_INTENT_TYPE`), `layout_leakage_rate`. All four safety-adjacent metrics score 0%/100% as required; see the final report for the actual run.

## 15. Known limitations and scoping decisions (stated honestly)

- **Document scope only, not per-section.** §3 explains why. A future milestone that wants section-scoped commands needs a real, structural bridge from M3.2/M3.3/M3.4 content-reference ids to `ContentModel.ContentBlock.id` — this milestone does not build one, because none exists to build on top of safely.
- **No `preserve_content`/`remove_content` generation.** For the same reason as above: this compiler has no real signal that names a `ContentBlock` id, so it never fabricates one. Both `IntentType`s remain fully supported by `validate_intent`/`apply_intent` and by this package's own validation (CMD-003 exists specifically to guard `remove_content` if a future generator or a hand-built plan ever proposes one) — they are simply never *generated* by `RuleBasedCommandGenerator`/`LLMCommandGenerator` today.
- **No `recompose_page` generation.** No `DesignIntent` field maps to "recompose with no change" as a genuine signal; synthesizing one would be policy without a real trigger.
- **Sequential, whole-document application only.** `/commands/apply` calls plain `compose()` for each step, not `compose_scoped()` — every command this package generates targets `TargetType.DOCUMENT`, so there is no page to scope to yet. `compose_scoped`/`resolve_scope` remain available (reused as vocabulary, never called by this package) for a future page-scoped command source.
- **Direction ids can accumulate an `-adj` suffix across chained commands** (`image-led` → `image-led-adj` → `image-led-adj-adj`) — this is `brand.creative.intent._derive()`'s own, pre-existing, documented behavior for any sequence of derived directions, unchanged by this milestone; confirmed during the live smoke test, not a regression introduced here.

## 16. Readiness for M3.6

`CommandPlan.metadata` and `GeneratedCommand.provenance`/`source_field` already carry enough for a future closed-loop milestone (M3.6) to know *why* each command exists and *which* `DesignIntent` field to re-check after applying it — the same "before/why/what/where/after" shape `brand.creative.iterate.IterationResult` already established for the M1.4/M1.5 loop. Nothing here needs to change shape for that loop to close; M3.6 would sit above this package the same way `iterate()` sits above `brand.creative.intent`, not inside it.
