# ADOS-M3.1 — Semantic Intent

## 1. What this milestone is, in one sentence

The first LLM layer in ADOS: natural language in, a typed, validated
`SemanticIntent` out — nothing executed, nothing mutated, and no
CommandIntent produced. That is the entire boundary this milestone
draws.

```
Natural Language -> LLM -> SemanticIntent -> deterministic validation -> (future M3 layers) -> CommandIntent
```

M3.1 implements only the first two arrows.

## 2. Why a new package, not an extension of the existing agent system

The repository already has an LLM convention —
`services/agents/base_agent.py`'s `BaseAgent`, used by `BrandAgent` and
the REVELATION-side agents (`ArchitectAgent`, `CarbonAgent`,
`ComplianceAgent`). It is Google Gemini, free-form text generation,
ad-hoc JSON extraction, and a deterministic rule-based fallback when no
key is configured.

ADOS-M3.1 explicitly requires the strongest structured-output
mechanism available, provider independence, and a domain model that
never touches a vendor SDK type. Rather than bend that existing
Gemini-shaped contract to fit, this milestone introduces `brand/llm/`
as ADOS's own LLM boundary, using Claude (`client.messages.parse`) as
its concrete provider — while keeping the same architectural posture
`BaseAgent` already established: a deterministic fallback so the
pipeline degrades, never breaks, and every automated test in this
repository runs without a network call or an API key.

`brand.creative.intent.CommandIntent` (ADOS-M1.2) is untouched. It sits
one layer below `SemanticIntent` in the eventual pipeline and is not
imported anywhere in `brand/llm/` — checked structurally, not just by
convention (`tests_brand/test_semantic_intent_extractor.py`).

## 3. SemanticIntent (`brand/llm/semantic_intent.py`)

A frozen pydantic model, `extra="forbid"`, doubling as the JSON-schema
source for Claude's structured output — one definition, matching
`brand/schemas/brand_schema.py`'s own "generated from the model, not
hand-duplicated" principle.

Every field lives in exactly one of three buckets, enforced by a
`model_validator`:

* `explicit` — what the user said.
* `inferred` — what was concluded from context; could be wrong.
* `ambiguous` — a list of field names that could not be safely
  resolved at all.

A field absent from all three simply was not addressed by the request.
`action` and `target` are the two fields every intent must resolve or
mark ambiguous — nothing downstream is actionable without knowing at
least what was asked and what it was pointed at.

Sixteen fields total (`SemanticFieldValues`): `action`, `target`,
`document_type`, `purpose`, `audience`, `subject`, `style_reference`,
`brand_reference`, `quality_direction`, `design_direction`, and six
list-valued free-text fields (`content_requirements`,
`style_requirements`, `design_requirements`, `constraints`,
`references`, `modifiers`). There is deliberately no `page_count`,
`font`, `grid`, `colour`, `image_count` or `layout` field — those
belong to later M3 phases, and a schema that has no slot for them
cannot accidentally invent one.

## 4. Vocabulary (`brand/llm/vocabulary.py`)

Two closed enums — `Action` (create, modify, regenerate, revise,
extend, summarize, transform, compare, review) and `Target` (document,
project, section, page, brand, content, presentation, portfolio,
report, template). `document_type` is deliberately **not** a third
closed enum: `known_document_type_ids()` resolves against
`brand.project.document_types.DOCUMENT_TYPES`, the one real registry —
a new Document Type added there as pure data (per ADOS-M2.5) is a
valid semantic target with zero change to this package.

## 5. Context (`brand/llm/context.py`)

`SemanticContext` is built only from real objects the caller actually
has — a `Project`, a `Brand`, a `DesignState`, prior conversation turns.
`available_document_types` and `available_capabilities` are always
populated (they are the registry and the vocabulary, not situational
data); everything else is `None` unless supplied. Nothing here fetches
arbitrary project data on the LLM's behalf — that is explicitly M3.2's
job.

## 6. Validation (`brand/llm/validation.py`)

Reuses `brand.validation.brand_validator`'s `Finding`/`Severity`/
`Category`/`ValidationReport` — the same structures
`brand.creative.evaluate` and `brand.project.requirements` already
report through. Ten checks (`SIN-001`..`SIN-010`): action/target
presence (BLOCK), unsupported action/target/document_type (ERROR),
malformed list entries (ERROR), a document_type set against a
non-document-shaped target (ERROR — contradiction), `compare` with
nothing to compare against (ERROR — impossible combination), a
create-document intent with no document_type resolved or marked
ambiguous (WARN), and high confidence alongside heavy inference (WARN).

Schema validity (pydantic) and domain validity (this module) are two
separate gates, exactly as ADOS-M3.1 §9 specifies — a schema-valid
`SemanticIntent` can still fail every check here.

## 7. Provider abstraction (`brand/llm/provider.py` + `providers/`)

```
LLMProvider.extract(system_prompt, context) -> (SemanticIntent, ProviderMetadata)
```

Two implementations:

* `ClaudeProvider` — `client.messages.parse(model="claude-opus-5",
  output_format=SemanticIntent, ...)`. No Anthropic SDK type ever
  crosses back out of `extract()`; every failure (auth, network,
  refusal, a malformed response) becomes a `ProviderError`.
* `RuleBasedProvider` — deterministic keyword matching, no network
  call ever. Conservative by construction: where it cannot confidently
  match a cue, it marks the field ambiguous rather than guessing. This
  is what every automated test in this repository actually exercises.

`SemanticIntentExtractor` (`brand/llm/extractor.py`) resolves Claude
when `ANTHROPIC_API_KEY` is set and `SEMANTIC_INTENT_LLM_ENABLED` isn't
`"false"`, and falls back to the rule-based provider on missing
credentials, a disabled flag, or any `ProviderError` — the identical
shape `services.agents.base_agent.BaseAgent.run` already uses.

## 8. Prompt (`brand/llm/prompt.py`)

Versioned (`PROMPT_VERSION`), split into a static system prompt (role,
ADOS's conceptual model, the closed vocabulary, the explicit/inferred/
ambiguous contract, worked examples, failure behaviour — the stable,
cacheable prefix) and a per-call user message (the actual request plus
whatever real `SemanticContext` was available). The registry and
vocabulary are never baked into the static prompt text itself, since
either can change between two calls sharing the same prompt version.

## 9. API (`api/routers/semantic_intent.py`)

```
POST /api/v2/intent/semantic          {request, project_id?, document_id?, version?, conversation?}
                                       -> {intent, validation, request_id, provider, model}
GET  /api/v2/intent/semantic/schema   -> {schema_version, schema}
GET  /api/v2/intent/semantic/traces           -> {traces: [...]}   (dev inspection)
GET  /api/v2/intent/semantic/traces/{id}      -> one trace
```

`project_id`/`document_id` resolve through the same repository and
`build_design_state()` call `GET .../design-state` already uses — real
context, or a 404 if the id doesn't exist. Nothing here writes
anything; the response never contains a `PagePlan`, a `document`, or a
`command_intent`.

## 10. Observability (`brand/llm/observability.py`)

An in-memory, bounded trace recorder (`SemanticIntentTrace`) — not a
database. Each trace carries a `request_id`, provider/model/prompt/
context versions, a truncated request preview (never the full
assembled context, which can carry a project description or a brand's
identity), the resulting `SemanticIntent`, the validation result, and
latency/token metadata. `GET /intent/semantic/traces` and the `/dev/
semantic-intent` frontend page are what ADOS-M3.1 §20's "developer-
facing inspection" actually means before M3.2 exists to build on it.

## 11. Evaluation (`brand/llm/evaluation.py` + `tests_brand/data/semantic_intent_eval.json`)

Fourteen cases — the three worked examples from the master prompt
(§14-16) verbatim, one case per basic action, two document-type
resolution cases, one "nothing to compare against" case that must fail
domain validation, and one deliberately unintelligible request. The
harness scores field accuracy, hallucination rate, schema validity, and
domain-validation-success against the deterministic rule-based
provider on every CI run; `scripts/run_semantic_intent_eval.py` runs
the identical dataset against the real Claude provider for a human to
read, whenever an API key is actually available — never part of the
automated suite.

## 12. What this milestone explicitly does not do

No CommandIntent is ever produced or applied. No `Composer` call. No
autonomous loop — one request in, one `SemanticIntent` out, full stop.
No page count, font, grid, colour, or layout value anywhere in the
schema. No project data is fetched on the LLM's behalf beyond what the
caller already supplied. No second document-type registry, no second
validation framework, no parallel command system.

## 13. Readiness for the next M3 phases

`SemanticIntent` is exactly the semantic-layer artifact M3.2
(`ContentModel`), M3.3 (`NarrativePlan`), M3.4 (`DesignIntent`) and
M3.5 (`CommandIntent`) can consume without re-deriving it from natural
language each time — a stable, versioned, JSON-serializable, provider-
independent representation of what a user wants, sitting strictly
above the deterministic ADOS engine it will eventually, through a
boundary this milestone does not itself cross, help drive.
