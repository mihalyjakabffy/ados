# ADOS-M3.6 — LLM → ADOS Closed Loop

## 1. What this milestone is, in one sentence

Given a project's real Project/Document/Brand state, run a controlled, deterministic loop — DesignIntent → M3.5 commands → execute → compose → evaluate → Finding → Recommendation → DesignIntent patch → repeat — that observes the result of its own composition, identifies structured problems, proposes a bounded correction, and executes that correction through the canonical ADOS command system, stopping for an explicit, structured reason every time.

## 2. The architectural boundary, enforced structurally

Three postures this package holds simultaneously, verified at the AST level in `tests_brand/test_loop_boundaries.py`:

- **Orchestrate, don't replace.** Every domain object M3.6 produces (`DesignIntent`, `CommandPlan`, `PagePlan`, `Evaluation`, `Finding`) is the exact type M3.1-M3.5/M1.x already define. `brand/llm/loop/` adds an `Iteration` record, a `Recommendation`, and a `DesignIntentPatch` — nothing that competes with an existing schema.
- **Reuse the execution primitives, don't bypass them.** `brand/llm/loop/execution.py` is the *only* module in this package allowed to call `validate_intent()`/`apply_intent()`/`compose()` — mirroring `api/routers/command.py`'s own `/commands/apply` endpoint, not a second implementation of it. Every other module (`recommend.py`, `patch.py`, `findings.py`, `orchestrator.py`'s own planning half) is proven, by AST inspection, never to call them.
- **The LLM proposes, deterministic code decides.** The one bounded LLM call this package makes (`recommend.make_llm_proposer`) can only ever name one of seven closed `DesignIntent` fields and one real value for it — never a command, a coordinate, or a decision about whether the loop continues. Every stop condition, every regression/no-progress/oscillation check, is a plain Python comparison (`orchestrator.decide_outcome`), never a model's own judgement.

## 3. Repository reconnaissance (Phase 0)

Before writing anything, this milestone re-read `brand/creative/iterate.py` (M1.4/M1.5's own `RecommendationCapability`/`Recommendation`/`IterationResult`/`IterationHistoryEntry` pattern — the direct prior art for this milestone's own `Recommendation`/`Iteration` shapes), `brand/creative/evaluate.py` (the real `evaluate()` this milestone reuses unchanged), `brand/project/versioning.py` (`build_version`, the real version-append primitive `execution.save_new_version` reuses), and `api/routers/ados_project.py`'s `compose_document`/`save_version` endpoints (the sanctioned `model_copy` + `_repo().save()` persistence pattern this milestone's own execution layer follows exactly).

Two things fell out of that reading that shaped the design:

1. **M1.4/M1.5's own `recommend()`/`CAPABILITIES` registry maps a `Finding` straight to a `CommandIntent`** (`FILL_RATIO_LOW` → `change_page_direction`), skipping `DesignIntent` entirely — because it predates M3.4. ADOS-M3.6 explicitly wants `Finding → Recommendation → DesignIntentPatch → M3.5 → CommandIntent`, a layer that did not exist when M1.5 was built. This milestone does not replace M1.4/M1.5's own registry (it is untouched, still real, still usable directly against a `PagePlan`) — it introduces the *analogous* mechanism one layer up, in `brand/llm/loop/recommend.py`, following the exact same `RecommendationCapability` shape M1.5 established.
2. **`resolve_document_content(document, project)`** (`brand/project/content_resolution.py`) is the real function that turns a `Document`'s own structured content into a `brand.content.model.ContentModel` — the thing M3.5's own API (`api/routers/command.py`) required callers to supply inline because this function had not yet been found during that milestone's own reconnaissance. M3.6's orchestrator uses it directly, so a real Project/Document with real content items composes without any inline JSON payload — a genuine, honest improvement in realism over M3.5's own API ergonomics, made possible by reading one file M3.5 had missed.

## 4. Domain model (`brand/llm/loop/model.py`)

- **`Iteration`** — the canonical, immutable record (ADOS-M3.6 §5/§6). Embeds the real `DesignIntent`, `CommandPlan`, composed `PagePlan`, and evaluation in full — reproducibility means both iterations in "what changed between 3 and 4" remain exactly what they were, not a reference that could later resolve to something different.
- **`DesignIntentPatch`** — `target` (one of `PATCHABLE_FIELDS`: `composition_strategy`, `density`, `typography_hierarchy`, `color_strategy`, `grid_strategy`, `whitespace_strategy`, `rhythm` — the same document-level surface `brand.llm.command`'s own compiler already reads), `operation` (`SET` only today — no capability produces anything else, and inventing a second operation with no driver would repeat exactly the mistake M3.4's own model.py docstring warns against), `value`, `rationale`.
- **`Recommendation`** — Finding → Recommendation (§15). Never a `CommandIntent`; carries a `DesignIntentPatch`, `source` (`DETERMINISTIC`/`LLM`), `confidence` (`1.0` for deterministic, `0.6` for the bounded LLM path).
- **`FindingRecord`** — one real `Finding` (serialized, since `Finding` is a plain frozen dataclass) plus `status` (`OPEN`/`RESOLVED`/`REGRESSED`/…) and `first_seen_sequence`/`last_seen_sequence` — resolution tracking (§68/§69/§70).
- **`IterationPolicy`** — `max_iterations` (default 5), `autonomy`, `max_llm_calls` (default 10), `allow_llm_recommendation`, `max_repeated_recommendation_attempts` (default 2) — every configurable budget in one place, conservative defaults (§33/§38/§63/§64).

## 5. The state machine (`brand/llm/loop/vocabulary.py`, `orchestrator.py`)

**A deliberate scope decision, stated honestly**: `run_iteration()` runs synchronously from `PLANNING` to one terminal `IterationStatus` (`COMPLETED`/`STOPPED`/`FAILED`/`BLOCKED`/`AWAITING_APPROVAL`) within one call — this package does not implement a resumable, externally-driven state machine persisting intermediate states between separate network calls. The full ADOS-M3.6 §4 stage sequence is still real and recorded, in order, on `Iteration.stage_log` — an audit trail proving every stage a given iteration actually reached, not a set of independently-resumable states. `resume_iteration()` is the one place a *pending* iteration (`AWAITING_APPROVAL`) is picked back up, re-using its already-computed `DesignIntent`/`CommandPlan` rather than re-planning.

`decide_outcome()` is the one pure function both `run_iteration` and `resume_iteration` call for the terminal decision — extracted specifically so it is unit-testable without running the full pipeline, and so the two call sites cannot drift:

```
regression (a REGRESSED finding at ERROR)      -> REGRESSION,  STOPPED
no ERROR/BLOCK findings remain                 -> SUCCESS,     COMPLETED
findings remain but no recommendation exists   -> NO_ACTIONABLE_RECOMMENDATION, BLOCKED
same findings + same DesignIntent as parent     -> NO_PROGRESS, STOPPED
otherwise                                       -> None (continue), COMPLETED
```

Order matters: regression is checked first because "fewer findings" is not the same claim as "no new problem" (§30).

## 6. Version safety (`orchestrator.py`, ADOS-M3.6 §7)

Every iteration after the first checks `parent.output_design_state_version == build_design_state(...).version.number` before doing anything else. A mismatch — the state moved between one iteration's completion and the next one's start — stops immediately with `StopReason.STALE_STATE`, no content resolved, no `DesignIntent` regenerated, no mutation. This reuses `brand.project.versioning`'s real version numbers; no second version scheme was introduced.

## 7. Evaluation (`brand/llm/loop/findings.py`)

`collect_findings()` calls the real `brand.creative.evaluate.evaluate()` unchanged, and folds in one honest extension: a real `DesignIntent.design_issues` (M3.4's own flagged tensions) becomes a coded, `WARN`-severity `Finding` (`DESIGN_ISSUE_BRAND_CONFLICT`, etc.) — the same vocabulary the loop already reasons over, not a second "something is wrong" system. `classify_findings()` compares this iteration's findings against the latest known record per fingerprint across the lineage, producing `OPEN`/`RESOLVED`/`REGRESSED` — a finding is never marked resolved merely because a command executed (§68); it is resolved only when a subsequent `evaluate()` no longer raises it.

**Finding identity** (`brand/llm/loop/fingerprint.py`, §69) is `(code, metric)` for a coded finding — deliberately not `page_index` (a document-scoped command can shift page counts between iterations) and not the free-text `message`. A finding with no `code` (most of `evaluate()`'s own conformance checks — Composer-implementation defects, not design decisions this loop patches) falls back to `(field, category, message-hash)`. **A real bug was caught here by this milestone's own live browser smoke test**: two different codeless findings legitimately share `field="plan"` (`evaluate.py`'s own pacing-match and rejected-candidate checks) — the first fingerprint design (`field` alone) collided them, producing a duplicate React list key in `/dev/closed-loop`. Fixed by including `category` and a message hash for the codeless fallback; a regression test now locks this in (`test_uncoded_findings_sharing_a_field_but_different_category_or_message_do_not_collide`).

## 8. Recommendation (`brand/llm/loop/recommend.py`)

A small, deterministic capability registry — three entries, mirroring `brand.creative.iterate.CAPABILITIES`'s own one-entry honesty about staying small:

| Finding code | Patch | Why exactly this fix |
|---|---|---|
| `FILL_RATIO_LOW` | `composition_strategy = image_led` | The same lever `brand.creative.iterate`'s own FILL_RATIO_LOW capability uses, expressed as a DesignIntent field |
| `FILL_RATIO_HIGH` | `density = low` | Lowers the target text density so the page fits under the fill-ratio ceiling |
| `DESIGN_ISSUE_BRAND_CONFLICT` | `typography_hierarchy = restrained` | The direct fix for exactly the tension M3.4's own DES-009 flags |

Every other `DesignIssueType` (asset scarcity, contradictory density, unsupported visual inference, missing content acknowledged) has no safe automatic fix and is always recorded as `SkippedRecommendation(reason=NO_SAFE_COMMAND_EXISTS)` — asset scarcity needs more assets, not a strategy change, and this package does not guess. A finding with no `code` is recorded as `UNSUPPORTED_SCOPE` — a Composer-level defect has no `DesignIntent`-level correction. Related findings that fingerprint identically (the same code, regardless of which page) naturally collapse to *one* recommendation, not one per instance (§25) — no separate clustering engine was built; the fingerprint identity already does this.

The bounded LLM tie-breaker (`make_llm_proposer`) only ever runs for the single highest-priority coded finding with no deterministic capability, and its structured-output schema (`RawPatchChoice`) has fields for nothing but `target`/`value`/`rationale` — proven at the AST level to carry no command-shaped field.

## 9. DesignIntent patching (`brand/llm/loop/patch.py`)

`apply_design_intent_patch()` mirrors `brand.creative.intent._derive()`'s own discipline exactly: the patched `DesignIntent` is built via `DesignIntent.model_validate()` (full pydantic construction, every validator re-run), never `model_copy` (which would skip them), and is additionally re-checked by the real `brand.llm.design.validation.validate_design_intent()` before this function ever returns it. A patch producing a `DesignIntent` M3.4's own validator would reject is refused here, not downstream (§51).

## 10. Execution (`brand/llm/loop/execution.py`)

`gate_commands()` implements the autonomy policy (§37/§38) by reusing `brand.llm.command.vocabulary.CommandSafetyLevel` as the gate — `NONE`/`RECOMMEND` require approval for everything; `SAFE` (the default) auto-executes only `SAFE`-labelled commands; `FULL` auto-executes everything M3.5's own validator already accepted. `execute_commands()` calls `validate_intent()` immediately before every `apply_intent()` call, composing after each command so the next one sees the real, current document — and, when zero commands are needed, still composes once from the unchanged content/direction so there is always something real for evaluation to observe. `save_new_version()` persists a composed `PagePlan` exactly the way `api/routers/ados_project.py`'s own `compose_document`/`save_version` endpoints already do: `Document.latest_plan` updated, a new immutable `ProjectVersion` appended via the real `build_version()`, `model_copy` throughout — the sanctioned write path every Project-mutating endpoint in this repository already uses, not a second one.

## 11. Observability (`brand/llm/loop/observability.py`)

The same bounded in-memory store pattern every M3 layer uses, keyed by `(project_id, document_id)` since a lineage — the immutable iteration history a "what changed" question needs — belongs to one document's timeline, not one request. No `Iteration` is written into `Project`/`Document` storage; a process restart loses iteration history the same way it already loses every other M3 layer's traces.

## 12. API (`api/routers/closed_loop.py`)

`POST .../loop/start` (first iteration, 409 if a lineage already exists), `POST .../loop/continue` (next iteration, 409 if the lineage already stopped), `POST .../loop/run` (start-and-run-to-completion), `POST .../loop/approve` (resumes a pending iteration), `POST .../loop/stop` (marks the lineage user-stopped; a no-op on an already-terminal one), `GET .../loop` (history), `GET .../loop/{id}` (one iteration in full), `GET .../loop/{id}/trace` (the condensed decision trace), `GET /loop/schema`. `dry_run=True` on `start`/`continue` plans, generates, validates, executes and composes entirely in memory and never calls `save_new_version` (§57) — verified: the returned `Project`/`Document` are the same objects passed in.

## 13. Frontend (`ados-web/app/dev/closed-loop/page.tsx`)

An iteration timeline, a live pipeline visualization (the nine stages, highlighting which ones `stage_log` actually reached), and per-iteration panels for commands, findings, recommendations, skipped recommendations, and metrics — Start / Continue / Run full loop / Approve / Stop actions, with autonomy and max-iterations controls.

## 14. Evaluation (`brand/llm/loop/evaluation.py`)

**A deliberate deviation from M3.2-M3.5's own JSON-dataset pattern, stated honestly**: most of ADOS-M3.6's own 15 scenarios (§65, A-O) are claims about *behaviour across steps* (a stop condition, a monotonic trend, a repeated-state detection) that a single input/output row cannot express. Each of the 15 scenarios below is a small Python function exercising the real orchestrator/recommendation/decision code directly — never a reimplementation of it — against fixed, deterministic fixtures. All 15 pass; `hallucination_rate`, `unsafe_execution_rate`, `stale_execution_rate`, and `bypass_rate` are all 0%.

| Case | What it proves |
|---|---|
| A | No blocking findings → `SUCCESS`, regardless of any recommendation |
| B | One finding → one recommendation → resolved next iteration → `SUCCESS` |
| C | Two identical-fingerprint findings (same code, different page) → exactly one recommendation |
| D | Two findings with distinct capabilities → sequential, independent fixes |
| E | Same findings + same DesignIntent as parent → `NO_PROGRESS` |
| F | A resolved finding reappearing at ERROR → `REGRESSION` |
| G | `density=low → high → low` fingerprints identically at the start and end |
| H | A stale `output_design_state_version` → `STALE_STATE`, no mutation |
| I | A codeless finding → `UNSUPPORTED_SCOPE`, never guessed at |
| J | A hand-built invalid `CommandPlan` → CMD-001 catches it (M3.5's own validator, reused) |
| K | `autonomy=NONE` → `AWAITING_APPROVAL`; approving completes execution |
| L | `max_iterations=1` with an existing lineage → `MAX_ITERATIONS` |
| M | No `ANTHROPIC_API_KEY` → the deterministic generators still complete, zero LLM calls, never `PROVIDER_ERROR` |
| N | Three findings resolved one at a time → strictly monotonic decrease |
| O | A real `run_loop()` reaches every pipeline stage and a persisted, terminal outcome |

## 15. Safety boundaries (AST-verified, `tests_brand/test_loop_boundaries.py`)

No `eval`/`exec`/`subprocess`/`os.system` anywhere in the package or its router; no raw SQL; only `execution.py` may call `apply_intent`/`compose`; `execution.py` is proven to call `validate_intent` before `apply_intent`; `orchestrator.py` is proven never to call the execution primitives directly (it delegates to `execution.py`); no module defines a second `CommandIntent`/`PagePlan`/`Page`/`Slot`/`DesignState`/`Project`/`Document` type; `execution.py`'s Project/Document mutation is proven to happen only through named, sanctioned locals (`project`/`document`/`new_project`/`new_document`), never arbitrary attribute assignment; the version-safety check (`output_design_state_version`/`StopReason.STALE_STATE`) is present in the orchestrator's own source; the bounded LLM proposer's schema is proven to carry no command-shaped field.

## 16. Known limitations (stated honestly)

- **Synchronous, non-resumable state machine.** One `run_iteration()` call runs start-to-finish; there is no persisted, independently-resumable intermediate state between the nine internal stages — only the completed stage list (`stage_log`). A future milestone wanting true async/distributed step-by-step execution would need to add that; this milestone's own scope (§84: "keep the implementation narrow enough to be trustworthy") does not require it.
- **Document scope only**, inherited directly from M3.5: every `DesignIntentPatch` targets a document-level field. No per-section/per-block correction exists, for the same reason M3.5 never built one (§55): no structural bridge from M3.2-M3.4 content-reference ids to `ContentModel.ContentBlock.id` exists anywhere in the shipped system, and this milestone does not invent one.
- **A small, honest capability registry** (three entries) rather than a general "any finding can be fixed" claim. Every finding outside those three is recorded as skipped with a real reason, never silently dropped and never guessed at.
- **No LLM-as-judge.** Evaluation is entirely the real, deterministic `evaluate()` plus the coded `DesignIssue` bridge — no supplemental LLM evaluation signal was added, since none of the 15 scenarios required one and adding one un-requested would be exactly the overbuilding §84 warns against.
- **Oscillation detection is period-based on the `DesignIntent` fingerprint**, not a general cycle detector over arbitrary state — sufficient for the master prompt's own worked example (`low → high → low`) and verified directly (Case G), but a longer, non-repeating drift pattern would not trip it.

## 17. Confirmation

The ADOS-M3 closed loop is complete: `LLM → structured proposal → domain model → deterministic validation → CommandIntent → validate_intent() → version check → apply_intent() → compose() → evaluate() → Finding → Recommendation → DesignIntent patch → repeat` is real, tested, AST-verified code, not a diagram. UNDERSTAND (M3.1) → KNOW (M3.2) → NARRATE (M3.3) → DESIGN (M3.4) → ACT (M3.5) → COMPOSE/EVALUATE/LEARN/REVISE/ACT AGAIN (M3.6) is the architecture this repository now runs, end to end, on real Project/Document/Brand state.
