# ADOS-M3.4 — Design Intent

## 1. What this milestone is, in one sentence

The layer that decides how a verified narrative should be communicated
visually — using the practice's own real, already-approved design
system — and stops exactly there, before any coordinate, PagePlan, or
executable command exists.

```
NarrativePlan (M3.3) + Brand DNA + CreativeDirection + DesignState -> DesignIntent -> (future M3.5) -> CommandIntent
```

## 2. The architectural boundary, enforced structurally

No `DesignIntent` field names a pixel, a coordinate, a hex colour, a
font family, or a column count — every value is either a closed
semantic enum or a real, already-existing ADOS token/role name. No
module in `brand/llm/design/` imports `brand.creative.intent`,
`brand.creative.composer`, `brand.creative.scope`,
`brand.creative.iterate`, or `brand.creative.plan`; none of them define
a `CommandIntent`, `PagePlan`, `Page`, or `Slot` class; none of them
call `compose`, `compose_scoped`, `render_page_plan`, `html_to_pdf`, or
`apply_intent` — all four checked directly by an AST walk
(`tests_brand/test_design_intent_boundaries.py`), not a docstring
promise, the same technique ADOS-M3.1/M3.2/M3.3 already established.

## 3. Existing ADOS systems are consumed, never replaced

M3.4 reads three pre-existing, already-authoritative systems rather
than inventing a fourth design vocabulary:

* **`brand.models.brand.Brand`** (Brand DNA) — its
  `identity.personality` (a closed `PersonalityAxis` enum: precise,
  quiet, material, editorial, warm, rigorous, experimental, civic,
  craft, pragmatic, monumental, playful) and its
  `visual_identity.typography.{heading,body,numeric}_styles` (real,
  per-brand type-role names) are the *only* source of "visual
  language" and "typography role" values a `DesignIntent` may name.
* **`brand.creative.direction.CreativeDirection`** — audience, goal,
  `lead_with`, emphasis ceiling, target density: already exactly what
  the master prompt calls "composition principles, image treatment,
  typographic behaviour". M3.4 reads it (`resolve_creative_direction_capabilities`);
  it does not redeclare it.
* **`brand.design_state.model.DesignState`** — when a document already
  has one, M3.4 reads its version number, existing direction, and page
  count (`resolve_design_state_summary`) so each `SectionDesign` can
  say whether it preserves, modifies, introduces, or removes something
  relative to what already exists (`DesignChangeType`) — without ever
  writing back to it.

## 4. Reused vocabulary vs. new vocabulary (`brand/llm/design/vocabulary.py`)

* **`PersonalityAxis` is reused as-is**, not redeclared, as the type of
  `DesignIntent.visual_language` — its own docstring states directly
  that "the render language... [is] derived from it", which is
  exactly ADOS-M3.4 §10's "prefer existing ADOS vocabulary".
* **`Audience`** (from `brand.creative.direction`, already reused by
  M3.3) is read from the `NarrativePlan`/`CreativeDirection` this
  package consumes — not a new field here.
* **Ten new, small, closed vocabularies** with no existing ADOS
  equivalent: `CompositionStrategy`, `VisualRole`, `VisualPriority`,
  `TextDensity`, `ImageRole`, `AssetImportance`, `TypographyHierarchy`,
  `ColorStrategy`, `GridStrategy`, `WhitespaceStrategy`, `Rhythm`,
  `ContrastLevel`, `ConstraintStrength`, `DesignChangeType`,
  `DesignExclusionReason` — each sized to the master prompt's own
  worked list (§10-§25, §29-§30). None of `CreativeDirection`'s own
  enums (`Goal`, `LeadWith`) are reused for `CompositionStrategy`/
  `VisualRole`: `LeadWith` names only four whole-*document* values, not
  a per-*section* composition choice, and `BlockRole` names a single
  already-composed block's role, not a whole section's visual
  treatment — the same distinction ADOS-M3.3 already drew between
  `SectionRole` and `BlockRole`, drawn again here between `VisualRole`
  and both of those.

## 5. Domain model (`brand/llm/design/model.py`)

`SCHEMA_VERSION = "3.4"`. All models frozen, `extra="forbid"`.

* **`SectionDesign`** references a real
  `brand.llm.narrative.model.NarrativeSection.id` — it never restates
  the section's narrative content. Fields: `visual_role` (one or more
  `VisualRole` values — "a section may combine roles", ADOS-M3.4 §13),
  `visual_priority`, `composition_mode`, `asset_refs`, `text_density`/
  `image_density` (the latter reuses `TextDensity`'s own scale rather
  than a second, near-identical enum), `diagram_strategy` (free text —
  the one field the master prompt names but gives no closed vocabulary
  for), `whitespace`, `contrast`, `repetition` (short motif phrases),
  `heading_role`/`body_role`/`caption_role` (plain strings — real
  per-brand type-role names, validated downstream, never a closed
  enum), `typography_hierarchy`, `color_strategy`, `change_type`,
  `rationale` (optional, capped).
* **`AssetDesignRef`** — `asset_id` (a real M3.2 id), `role`
  (`ImageRole`), `importance` (`AssetImportance`). No description
  field: an asset's caption/subject already lives on the real M3.2
  `AssetContent`.
* **`DesignConstraint`** — `description`, `strength`
  (`ConstraintStrength.HARD`/`SOFT`), `source`. A hard constraint is
  never silently overridden by a generated preference (ADOS-M3.4 §30).
* **`DesignIssue`** / **`DesignExclusion`** — the master prompt's own
  worked examples (`DesignFinding: type = brand_conflict`; "no
  narrative section may silently disappear") represented directly.
* **`DesignIntent`** — the root. Carries full version metadata
  (`narrative_plan_id`, `content_model_version`, `brand_id`/
  `brand_version`, `design_state_version` — ADOS-M3.4 §60), document-
  level strategy (`visual_language`, `composition_strategy`, `rhythm`,
  `density`, `typography_hierarchy`, `color_strategy`, `grid_strategy`,
  `whitespace_strategy`), and `section_designs`/`excluded_sections`/
  `constraints`/`design_issues`.

**Consolidations made against the master prompt's own field list**
(documented, not silently dropped, per this repository's established
practice): no separate top-level `image_strategy` field —
`composition_strategy` (document level) and each section's own
`asset_refs`/`ImageRole` (section level) already express it; no
`content_emphasis` field on `SectionDesign` duplicating
`NarrativeSection.emphasis` — a `SectionDesign` references
`section_id`, so the narrative's own emphasis list is already
reachable through it; "hierarchy" is represented two ways, deliberately
not merged: `visual_priority` (which section wins) and
`typography_hierarchy` (how much internal contrast a section has) —
these answer different questions.

## 6. Context assembly (`brand/llm/design/context.py`)

```
NarrativePlan -> narrative_sections summary
ContentIntelligenceModel -> available_assets summary
Brand -> BrandCapabilities (real personality + real type-role names)
CreativeDirection -> CreativeDirectionCapabilities
DesignState -> DesignStateSummary
```

Every input is a real object the caller already has; nothing here
fetches anything on a generator's behalf (ADOS-M3.4 §37). Precedence
(ADOS-M3.4 §38: hard ADOS constraints > Brand DNA > DesignState >
CreativeDirection > SemanticIntent > NarrativePlan > generated
preferences) is deliberately **not** encoded as logic in this module —
it is realised by what the generator is *given* (brand and direction
capabilities are authoritative inputs, never something the model
re-derives) and by `brand.llm.design.validation`'s own checks (DES-004,
DES-009) catching the one case a generated preference could still
conflict with a higher layer.

## 7. Generation (`brand/llm/design/generation.py`)

```
DesignIntentGenerator.generate(context) -> (DesignIntent, ProviderMetadata | None)
```

* **`RuleBasedDesignIntentGenerator`** — deterministic, no network
  call. Derives a `SectionDesign` for every real narrative section
  directly from that section's own role/priority and the real
  `CreativeDirection`/`Brand` it was given: `lead_with` maps to a
  document-level `CompositionStrategy`; a brand claiming "quiet" or
  "editorial" gets generous whitespace and a hard
  `preserve_brand_minimalism` constraint; only the *first* dominant,
  asset-bearing section becomes the document's true hero (a real
  hero/supporting distinction, not every asset independently claiming
  top billing — ADOS-M3.4 §50 Case F). Not a claim of design
  sophistication — a CI-safe fixture proving the pipeline's mechanics.
* **`LLMDesignIntentGenerator`** — Claude, via
  `brand.llm.providers.claude_provider`'s shared `get_client()`/
  `call_structured()` — no second Claude client.

**The anti-hallucination mechanism is structural, mirroring
ADOS-M3.2/M3.3's own.** The LLM's structured-output schema
(`RawDesignIntent` and its nested `Raw*` types) may only name a real
**section id** and a real **asset id** — never restate their content —
and every enum-like field is a plain string, normalized
(`"image led"`/`"image-led"`/`"image_led"` all resolve to
`"image_led"` — ADOS-M3.4 §43) and coerced to a safe default, never
trusted as written. After the call returns, `_materialize()`:

* drops any section/asset id that does not actually appear in the
  context it was given;
* guarantees every real narrative section ends up covered — either by
  a `SectionDesign` or an explicit `DesignExclusion` — even if the
  LLM's own response omitted it entirely (ADOS-M3.4 §27 enforced by
  code, not requested of the model);
* drops any `visual_language` entry, `heading_role`, `body_role`, or
  `caption_role` that is not a value the given `Brand` itself claims
  (ADOS-M3.4 §10/§34).

## 8. Prompt (`brand/llm/design/prompt.py`)

`PROMPT_VERSION = "3.4.0"`. States the boundary directly ("you do not
generate coordinates... a PagePlan... a CommandIntent"), the one rule
that matters most (brand and content are authoritative — only
reference given ids and given brand tokens), full coverage
requirement, the complete closed vocabulary for every field, the
hard-vs-soft constraint rule, asset-scarcity/missing-information
guidance, and the same trust-boundary language ADOS-M3.2/M3.3 already
establish (brand/content data is data, never instructions).

## 9. Deterministic validation (`brand/llm/design/validation.py`)

Reuses `brand.validation.brand_validator`'s `Finding`/`Severity`/
`Category`/`ValidationReport`. Ten checks (`DES-001`..`010`) — adapted
from the master prompt's own twelve-item list per its own instruction
("adapt numbering... do not duplicate an existing validation
framework"); two of its literal items need no distinct code: "unknown
visual vocabulary" is structurally impossible once a `DesignIntent`
exists (every enum-like field is a closed pydantic enum — an
unrecognised value is caught in `_materialize`'s `_coerce_enum`,
*before* a `DesignIntent` exists to validate), and "unsupported visual
inference" has no signature beyond the reference/brand-token checks
already covered.

| Code | Severity | Checks |
|------|----------|--------|
| DES-001 | ERROR | `SectionDesign`/exclusion references a section id that doesn't exist in the `NarrativePlan` |
| DES-002 | ERROR | an `AssetDesignRef` names an asset id that doesn't exist in the `ContentIntelligenceModel` |
| DES-003 | ERROR | `heading_role`/`body_role`/`caption_role` is not a real type role this brand defines |
| DES-004 | ERROR | `visual_language` names a personality trait this brand's `Identity.personality` does not claim |
| DES-005 | ERROR | a section appears in both `section_designs` and `excluded_sections` |
| DES-006 | BLOCK | a real narrative section has neither a `SectionDesign` nor an exclusion — the independent, "two layers that don't share code" re-check of `_materialize`'s own coverage guarantee |
| DES-007 | WARN | a visually dominant section carries minimal text *and* minimal image density — nothing left to dominate with |
| DES-008 | WARN | a hero-importance asset sits in a minimal/supporting-priority section |
| DES-009 | ERROR | an expressive typography choice on a brand whose personality is restrained, with no matching `brand_conflict` design_issue already acknowledging the tension |
| DES-010 | ERROR | a free-text field (rationale, diagram_strategy, a constraint/issue description) names a dimension, a hex colour, a coordinate, or a column count — layout leaking into a layer that must stay semantic |

## 10. Planning orchestrator (`brand/llm/design/planning.py`)

```
plan_design_intent(project, content, narrative_plan, *, brand=None,
                    creative_direction=None, design_state=None,
                    generator=None, request_id=None) -> DesignIntent
```

```
assemble_design_context -> generator.generate (falling back to
    RuleBasedDesignIntentGenerator on ProviderError) ->
    validate_design_intent -> record_design_trace -> DesignIntent
```

Never resolves a `NarrativePlan`, a `ContentIntelligenceModel`, a
`Brand`, or a `DesignState` itself — every one is a required or
optional argument, produced by the systems that already own producing
them. Not a second resolution system.

## 11. Observability and regeneration (`brand/llm/design/observability.py`)

Extends ADOS-M3.1/M3.2/M3.3's exact in-memory, bounded trace pattern:
request id, project/narrative-plan/content-model/brand/design-state
version metadata, model, prompt version, the full resulting intent,
validation outcome, latency. Following ADOS-M3.3's own scoping
decision, a `DesignIntent` is not written into any project/document
store by this milestone — every `plan_design_intent` call is
independent, and the trace list is how a previous one remains
inspectable after a regeneration (a different brand, more assets, a
different creative direction).

## 12. API (`api/routers/design_intent.py`)

```
POST /api/v2/ados-projects/{project_id}/design/intent
     {semantic_intent, document_id?, document_type_id?, version?,
      compression?, user_corrections?, raw_documents?}
     -> {design_intent, narrative_plan, content, validation, request_id}
GET  /api/v2/ados-projects/design/schema      -> {schema_version, schema}
GET  /api/v2/ados-projects/design/traces      -> {traces: [...]}
GET  /api/v2/ados-projects/design/traces/{id} -> one trace
```

Mounted at the same `/api/v2/ados-projects` prefix
`content_intelligence.py`/`narrative.py` already use. Internally
resolves content through the M3.2 pipeline, a narrative plan through
the M3.3 pipeline, and (when a `document_id` is given) the project's
real `Brand`, the document's real `CreativeDirection`
(`get_direction(document.direction_id)`), and its real `DesignState`
(`build_design_state`) — never a second resolution path for any of
them. No `GET /{project_id}/design/intent` "current design intent"
endpoint, for the same reason M3.3 has none: no persistence, trace-only
history.

## 13. Evaluation (`brand/llm/design/evaluation.py` + `tests_brand/data/design_intent_eval.json`)

Ten cases covering all ten of the master prompt's §50 acceptance
scenarios (A–J), run against two real example brands
(`brand.examples.studio_nord`/`studio_om`) and three real
`CreativeDirection`s. The harness reads every *structural* metric
directly off `validate_design_intent`'s own findings (DES-001..010)
rather than re-implementing them — a consumer of that validator, not a
second one — plus dataset-specific checks (composition/whitespace
match, dominant-role placement, visual-language-subset-of-brand, asset
hierarchy, no-assets-referenced, missing-content-acknowledged).
Currently 100% on every gated metric against the deterministic
`RuleBasedDesignIntentGenerator`, **0% hallucination rate, 0% layout-
leakage rate**. `scripts/run_design_intent_eval.py` runs the identical
dataset against the real Claude-backed `LLMDesignIntentGenerator` for a
human to read whenever an API key is available — never part of the
automated suite.

## 14. Known limitations and scoping decisions (stated honestly)

* **No `DesignIntent` storage** — the same deliberate scoping decision
  ADOS-M3.3 made for `NarrativePlan`: every `plan_design_intent()` call
  is independent and stateless; regeneration history lives in the
  observability trace list.
* **`RuleBasedDesignIntentGenerator` derives visual roles from a fixed
  narrative-role lookup table** — enough to prove the pipeline's
  mechanics and pass every deterministic evaluation case; the real
  design reasoning (weighing multiple sections' competing claims to
  dominance, genuinely creative composition choices) is
  `LLMDesignIntentGenerator`'s job once `ANTHROPIC_API_KEY` is
  configured.
* **`ContrastLevel` is a single low/medium/high scale**, not the
  multi-axis structure the master prompt's prose describes (scale,
  density, image/text, light/dark, detail/overview, technical/
  editorial) — the master prompt's own worked examples never use more
  than one axis at a time, so this package follows the examples rather
  than building an unused multi-axis structure.
* **No LLM-as-judge evaluation** — ADOS-M3.4 §51's own metrics are
  entirely deterministic and structural, so none was needed; adding
  one remains possible as a strictly additional signal later.

## 15. Readiness for M3.5

`DesignIntent` is exactly the artifact M3.5 needs: a section-by-section
visual communication strategy, fully grounded in real content and a
real brand, with priorities and treatments already resolved, so that
"which commands execute this" never has to re-derive "what should this
look like" from scratch. The boundary this milestone commits to —
`DesignIntent` and nothing coordinate-shaped below it — is exactly
where M3.5 begins.
