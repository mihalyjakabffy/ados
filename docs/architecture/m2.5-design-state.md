# ADOS-M2.5 — Design State / Universal Document Model

## 1. What changed, in one sentence

ADOS stopped thinking "I am generating an Investor Deck" and started
thinking "I have a `DesignState`; an Investor Deck is one possible
projection of it" — without rebuilding, duplicating, or replacing any of
the M1.x/M2.x engine that already worked.

## 2. DesignState is a read model, not a second store

The single architectural decision everything else in this milestone
follows from: **`DesignState` is assembled on read from the real,
already-persisted domain objects** — `Project`, `Document`, `Brand`,
`PagePlan`, `CreativeDirection`, `Requirements` — never a parallel
storage system with its own id, its own table, its own save path.

```
brand/design_state/build.py::build_design_state(project, document, brand, *, version_number=None)
    -> brand/design_state/model.py::DesignState
```

This is what satisfies the master prompt's own prohibited-shortcuts list
in one stroke: there is no second Composer, no second layout engine, no
duplicated Brand model, and no risk of the read model drifting from the
real state, because it *is* the real state, reshaped.

```
Project ──┐
Document ─┼─→ build_design_state() ─→ DesignState (frozen, JSON-safe)
Brand ────┘        │
                    ├─ ProjectState        (brand/project/model.py::Project)
                    ├─ BrandState          (brand.models.brand.Brand.resolve_tokens())
                    ├─ ContentState        (Document.content_items + Project.content_items)
                    ├─ DocumentState       (Document + its DocumentType)
                    ├─ PageState/ComponentState/LayoutState  (Document.latest_plan, a real PagePlan)
                    ├─ VisualLanguageState (the document's CreativeDirection)
                    ├─ AssetState          (Project.assets)
                    ├─ ConstraintState     (brand.project.requirements.check_requirements)
                    └─ VersionState        (brand.project.versioning)
```

Nothing here calls `compose()`. A `DesignState` reflects whatever the last
real composition produced — the same "never invent a page the Composer
didn't produce" rule `Document.latest_plan` has always followed.

## 3. The schema (`brand/design_state/model.py`)

All models are frozen Pydantic models (`extra="forbid"`), so a `DesignState`
is immutable once built, round-trips through `json.dumps(json.loads(...))`
byte-for-byte via `.to_dict()` (`model_dump(mode="json")`), and carries an
explicit `schema_version: str = "2.5"` field for forward migration.

| Sub-state | Source | Notes |
|---|---|---|
| `ProjectState` | `Project` | id/name/description/`project_data`/document_ids — independent of any one Document |
| `BrandState` | `Brand.resolve_tokens()` | empty (`id=None`) when no brand is attached yet — a real, inspectable state, not an error |
| `ContentState` | `Document.content_items` + `Project.content_items` | `own` vs `shared_pool`, plus `selected_shared_ids` — the ADOS-M2.5 §6 mechanism |
| `DocumentState` | `Document` + its `DocumentType` (if any) | `output_type` is the projection id; audience/purpose come from the registry, `None` for an untyped/custom document |
| `PageState` / `ComponentState` | the document's `PagePlan` | components use a semantic vocabulary (`Text`, `Heading`, `Image`, `Metric`, `Diagram`, `Card`, `Caption`, `SectionHeader`, ...), mapped from the composer's own slot-component strings via a lookup table — **not** a new slot system |
| `LayoutState` | the plan's own grid | columns/gutter/margin/page size — the same deterministic grid the layout solver already produces |
| `VisualLanguageState` | `CreativeDirection` | audience/goal/lead_with/narrative_order/emphasis/density/pacing — separate from Brand and Layout by construction (Component = WHAT, Layout = WHERE, VisualLanguage = HOW) |
| `AssetState` | `Project.assets` | stable ids, filename, content-type, dimensions |
| `ConstraintState` | `brand.project.requirements` | MUST/SHOULD/MAY, mapped directly from the existing `Severity` enum (BLOCK/ERROR→MUST, WARN→SHOULD, INFO→MAY) — one severity scale, not two |
| `VersionState` | `brand.project.versioning` | `available_versions`, and (when version-scoped) `number`/`label`/`created_at` |

## 4. Document Type → Projection

`brand/project/document_types.py`'s `DocumentType` registry **already was**
the projection layer — a `DocumentType` is a lightweight configuration
(default structure, requirements, composition profile), never an
independent composition engine, and every type already composes through
the one shared `compose()`/`evaluate()` pair (proven for all eleven types
in `tests_brand/test_nine_document_types.py`). ADOS-M2.5 did not need to
introduce a `DocumentProjection` class; it needed to prove the registry
really behaves like one, and it does:

- **Two new projections were added as pure data**: `investor-deck` and
  `tender-document`, each a `DocumentType` entry plus a handful of
  `Requirement`s built from checkers (`required_section_present`,
  `required_metadata_present`) that already existed. Zero changes to the
  composer, evaluator, or requirements engine.
- **Website is an export *format*, not a new Document Type or renderer.**
  `ExportRequest.format: "pdf" | "html"`. `render_page_plan()` already
  produces the HTML the PDF pipeline prints through Chromium; the `html`
  format simply writes that same HTML out directly and skips
  `html_to_pdf`/Chromium entirely for that request. See
  `api/routers/ados_project.py::export_document`.

## 5. Content sharing: the "same content, multiple projections" mechanism

- `Project.content_items: tuple[ContentItem, ...]` — a new, shared pool at
  the project level, reusing the existing `ContentItem` type unchanged.
- `Document.content_selection: tuple[str, ...]` — a new, additive, opt-in
  field: ids into the project's pool this document includes, alongside its
  own private `content_items` (unchanged, so every pre-M2.5 document is
  100% unaffected).
- `brand/project/content_resolution.py::resolve_document_content()` merges
  a document's own items with its resolved shared selection, then applies
  the unchanged portfolio-chapter (`project_refs`) logic on top.
- **Version immutability under a mutable shared pool**: since the shared
  pool can change after a document last touched it, `ProjectVersion` never
  freezes the *selection* — it freezes the fully-**resolved** union (own +
  shared) at save time (`brand/project/versioning.py::resolve_full_content`
  inside `build_version()`). "What did the project look like at Version 7"
  stays true even if the shared pool is edited afterward.

API surface (`api/routers/ados_project.py`):

```
POST   /{project_id}/content                                  add a shared item
GET    /{project_id}/content                                  list the shared pool
DELETE /{project_id}/content/{item_id}                        remove a shared item (fail-soft on dangling refs)
PUT    /{project_id}/documents/{document_id}/content-selection replace one document's selection
```

## 6. The API surface for DesignState itself

```
GET /{project_id}/documents/{document_id}/design-state[?version=N]
```

There is no `POST` to create a DesignState and no `design-states/{id}`
resource — there is nothing to create. The endpoint assembles one fresh
on every call from the project/document/brand already on disk. `brand` is
optional (a project without one still returns a real state, `brand.id ==
None`). `?version=N` reads a specific saved Version's frozen
content/plan through `brand.project.versioning.find_version()` — a
**read-only** lookup, distinct from the export pipeline's own
`resolve_version()`, which auto-saves a version when none is given. A
`GET` must never have that side effect.

## 7. Composition pipeline (unchanged, now framed as projections)

```
Project + Brand + Content  ──▶  Document (a Document Type / projection config)
                                     │
                                     ▼
                        brand.creative.composer.compose()
                                     │
                                     ▼
                                 PagePlan
                                     │
                        brand.creative.evaluate.evaluate() ──▶ Findings
                                     │
                    brand.project.requirements.check_requirements() ──▶ Requirement Findings
                                     │
                                     ▼
                         render_page_plan() ──▶ HTML
                                 ╱        ╲
                      html_to_pdf()      write directly
                        (Chromium)       (format="html")
                            │                  │
                           PDF               Website
```

`DesignState` sits *beside* this pipeline as a read projection of its
inputs and outputs — it is never in the call path of `compose()`.

```
Project → DesignState → CompetitionBookProjection(=competition-document) → PagePlan → PDF
Project → DesignState → WebsiteProjection(=format="html" on any Document Type) → HTML
```

The core state (`ProjectState`, `BrandState`, the shared content pool)
is identical across both — proven directly in
`tests_brand/test_cross_projection.py`.

## 8. Migration strategy

This was a refactor, not a rewrite. Every new field is additive and
defaults to empty/unset:

- `Project.project_data: dict = {}`, `Project.content_items: tuple = ()`
- `Document.content_selection: tuple = ()`
- `ExportRequest.format: str = "pdf"` (existing callers get identical
  behavior)

No existing field was renamed, removed, or repurposed. The full pre-M2.5
regression suite (M1.x + M2.x, 600+ tests) stayed green throughout every
phase — verified after every commit in this milestone, not just once at
the end.

## 9. Frontend

`DocumentContextPanel` gained one new section, **Shared Content** (a
project-level pool with per-document checkboxes wired to
`PUT .../content-selection`), and the Export section gained a second
button, **Export Website**, next to **Export PDF** — both call the same
`POST .../export` with a `format`. `Library | Canvas | Command` and the
rest of the panel are untouched, per §20's explicit instruction not to
redesign the UI for an underlying state-model change.

## 10. LLM readiness (not implemented — this milestone is the prerequisite)

`DesignState` exposes exactly the semantic primitives §17 asks for —
Project, Brand, Content, Document, Page, Component, Layout,
VisualLanguage, Asset, Constraint, Version — as a single, versioned,
JSON-serializable, renderer-independent, LLM-vendor-independent object.
It has no dependency on Claude/OpenAI/Gemini, no dependency on PDF or
HTML, and no dependency on any one Document Type. The existing
`CommandIntent` vocabulary (`CreateDocument`, `SetContent`, `ApplyBrand`,
...) already operates at this same semantic level (`brand/creative/intent.py`,
unchanged by this milestone). A future LLM layer sits *above* this
architecture — `User → LLM → CommandIntent → deterministic ADOS engine →
DesignState` — never inside it, and never as a substitute for a
projection or composition step that doesn't exist yet.

## 11. Extension points

- **A new Document Type / projection**: add a `DocumentType` entry to
  `brand/project/document_types.py` and, if needed, `Requirement`s built
  from existing checkers in `brand/project/requirements.py`. No
  composer, layout, or DesignState change required — proven by
  `investor-deck` and `tender-document`, added with zero engine changes.
- **A new export format**: extend `ExportRequest.format`'s pattern and add
  one branch in `export_document`, reusing `render_page_plan()`'s output
  — proven by `format="html"`.
- **A new semantic component kind**: add an entry to `build.py`'s
  `_COMPONENT_KIND` map; unmapped components already degrade safely to
  `"Text"`.
